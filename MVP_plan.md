# План разработки MVP: Система расписания

## 1. Синхронизация понимания (Understanding Lock)
✅ **ПОДТВЕРЖДЕНО ПОЛЬЗОВАТЕЛЕМ**
* **Стек:** FastAPI (Backend) + React (Frontend).
* **База данных:** PostgreSQL (разворачивается по предоставленному шаблону).
* **Очередь задач:** Redis (в связке с фоновыми воркерами Celery или ARQ для расчета).
* **Пользователи:** В MVP только одна роль (Администратор/Диспетчер). Без авторизации.
* **Ввод данных (Гибридный):**
  * *Excel:* Исходные массивы (учебные планы, часы, списки групп и преподавателей).
  * *Web UI:* Настройка правил и ограничений (конкретные "окна" и заблокированные дни для педагогов).

## 2. Журнал решений (Decision Log)

* **Решение 1 (Использование Postgres):** Уход от SQLite в пользу PostgreSQL. 
  * *Почему:* Требование инфраструктуры проекта, высокая надежность, готовность к масштабированию.
  * *Статус:* 🟢 Утверждено.
* **Решение 2 (Запуск алгоритма через Redis):** Одобрен Подход А (Асинхронные задачи). Выбран Redis в качестве пула и брокера задач(Task Queue). 
  * *Почему:* Тяжелый расчет алгоритма OR-Tools (`gpt.py`, который работает до 320с) надежно изолируется в фоновых воркерах; сервер API не перегружается, HTTP-запросы браузера остаются "быстрыми".
  * *Статус:* 🟢 Утверждено.
* **Решение 3 (Конфигурация данных):** Физическое разделение ввода. 
  * *Почему:* Ввод сотен строк учебных планов через веб-формы — мучение для администраторов (поэтому Excel). А вот настройка индивидуальных временных слотов для педагогов в Excel крайне неудобна (поэтому Web-интерфейс).
  * *Статус:* 🟢 Утверждено.

## 3. Архитектура и поток данных (Architecture & Data Flow)

### 3.1. Системная архитектура сервисов
1. **Frontend (React/Nginx):** Клиентское приложение со статической сборкой.
2. **Backend API (FastAPI):**
   * Предоставляет REST API для фронтенда.
   * Парсит загружаемые Excel-файлы и перекладывает в нормализованные таблицы SQL.
   * Передает команду «Посчитать» в очередь Redis и умеет отдавать статус расчета.
3. **Task Worker (Celery/ARQ Python):**
   * Специальный фоновый процесс, слушающий Redis.
   * При старте задачи он "выкачивает" актуальные данные из PostgreSQL, формирует Python-словари (заменяя старый `consts.py`), запускает ядро `solve_time_schedule()` + `assign_rooms()`.
   * Итоговый JSON расписания и конфликты сохраняет обратно в PostgreSQL, помечая задачу как `SUCCESS`.
4. **PostgreSQL:** Единое хранилище и точка правды.
5. **Redis:** Брокер задач + (опционально) быстрый кэш прогресса (например, сохранение % выполнения бара из консоли).

### 3.2. Ключевые экраны фронтенда (React Components)
1. **Экран "Импорт базовых данных":** Панель для перетаскивания (drag-and-drop) Excel-файла. Валидация колонок (Группы, Преподаватели, Часы).
2. **Экран "Преподаватели" (Редактор ограничений):** Список импортированных педагогов. При выборе открывается недельная сетка (календарь), где мышкой можно заблокировать часы, в которые данный человек не может вести пары (например, работает в другом месте).
3. **Экран "Панель управления":** Кнопка генерации. Вывод индикатора состояния (status bar) ответа из Redis.
4. **Интерактивный экран "Расписание":** 
   * Вывод рассчитанной сетки (матрица: Дни/Пары — Группы или Преподаватели).
   * Функционал Drag & Drop для перемещения карточек из слота в слот вручную.
   * Панель "Неразрешенные конфликты" (Красная / Желтая индикация, возвращаемая модулем Stage 2 `assign_rooms()`).
