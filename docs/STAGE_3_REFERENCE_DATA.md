# Этап 3. Базовые данные и правила

## Что нормализовано

Вместо констант и неструктурированных полей добавлены сущности:

- корпуса, аудитории и их оснащение;
- кафедры, дисциплины и настраиваемые виды занятий;
- требования потока к аудитории и оснащению;
- календарные правила доступности преподавателей, групп, аудиторий и вуза;
- профили правил генерации с признаком жесткости и весом каждого критерия.

Миграция `20260716_0004` переносит названия дисциплин из потоков, связывает
старые строки аудиторий с новым справочником и создает стандартный профиль.

## API

CRUD расположен под `/api/v1/reference`:

- `departments`, `buildings`, `rooms`, `room-features`;
- `activity-types`, `disciplines`;
- `availability`;
- `rule-profiles`;
- профили преподавателей и групп, требования потоков.

Старый экран календаря сохраняет JSON для обратной совместимости и одновременно
перезаписывает структурированные `AvailabilityRule`. Генератор использует новые
правила приоритетно, а JSON читает только для преподавателей без структурированных
настроек.

## Интеграция с solver

На этапе подготовки задачи из БД загружаются только активные аудитории. Глобальный
room matching учитывает:

- закрепленную за потоком аудиторию;
- вместимость и тип;
- обязательное оснащение;
- недоступность аудитории в конкретный слот.

Профиль выбирается через `settings.rule_profile_id`. Если параметр отсутствует,
используется активный профиль по умолчанию. Настройки управляют штрафами за
поздние пары, окна, предпочтения, последовательность лекций и практик, а также
жесткостью требований к аудиториям и обеденному перерыву.

## Проверка перед развертыванием

```bash
python -m pytest
ruff check src/app
cd spa && npm run build
cd ../src && alembic upgrade head
```

Перед миграцией production-БД необходимо сделать резервную копию. После запуска
следует проверить справочники в разделе «Базовые данные», назначить оснащение
аудиториям и привязать требования учебных потоков.
