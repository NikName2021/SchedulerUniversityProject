# Этап 2. Масштабируемая генерация

## Активный pipeline

Новая генерация выполняется в четыре фазы:

1. `ScalableGenerationService.prepare` загружает недельную нагрузку и формирует
   учебные события.
2. `build_conflict_components` строит граф по общим группам и преподавателям.
3. Celery chord параллельно запускает `scheduler.solve_component` для каждой
   независимой компоненты.
4. Callback `scheduler.finalize_schedule` объединяет результаты, глобально
   назначает аудитории и атомарно сохраняет версию расписания.

API-процесс только ставит родительскую задачу в Redis и не выполняет CP-SAT.

## Событийная модель

Переменная CP-SAT теперь означает «учебное событие поставлено в слот».
Потоковая лекция на десять групп создает одну переменную на слот, поскольку все
десять групп являются участниками одного события. Старая модель создавала десять
переменных и девять равенств для синхронизации на каждом слоте.

Семинары, практики и лабораторные занятия разворачиваются в отдельное событие
для каждой группы. Потоки идентифицируются через `stream_id`, поэтому одинаковые
названия дисциплин с разными преподавателями больше не объединяются.

## Безопасное разбиение

Два события находятся в одной компоненте, если у них есть общая группа или
преподаватель. Транзитивные связи также объединяются. Поэтому жесткие запреты
пересечений полностью решаются внутри одной CP-SAT-модели.

Аудитории не используются для объединения компонент. После решения времени
выполняется общая задача matching для каждого слота:

- одна аудитория назначается не более чем одному событию;
- нехватка вместимости и несовпадение типа учитываются штрафами;
- отсутствие аудитории допускается как диагностируемый частичный результат.

## Celery и прогресс

`GenerationTask` хранит:

- `total_components` и `completed_components`;
- `progress_percent`;
- итоговые метрики в `metrics_json`;
- идентификатор Celery chord.

Таблица `generation_component` хранит статус, число событий, переменных,
ограничений, время решения, objective и ошибку каждой компоненты. Диагностика
доступна через `GET /api/v1/scheduler/tasks/{task_id}/components`.

Число процессов worker задается переменной
`CELERY_WORKER_CONCURRENCY` (локальное значение — 4). Каждый CP-SAT процесс по
умолчанию использует два solver thread, чтобы не получить чрезмерную
переподписку CPU.

## Инкрементальный пересчет

Для локального пересчета в `settings` запроса генерации передаются:

```json
{
  "base_task_id": 42,
  "affected_stream_ids": [101, 102]
}
```

События указанных потоков пересчитываются. Остальные занятия базовой версии:

- копируются в новую версию расписания;
- блокируют свои группы, преподавателей и аудитории;
- не участвуют в CP-SAT-модели.

Занятия с `is_locked=true` остаются жестко зафиксированными и при полном, и при
локальном расчете.

## Защитные лимиты

Настройки задачи поддерживают:

- `max_total_events` — по умолчанию 20 000;
- `max_component_events` — по умолчанию 2 000;
- `max_component_seconds` — по умолчанию 120;
- `solver_workers` — по умолчанию 2;
- `room_assignment_max_seconds` — по умолчанию 5 на слот.

Превышение размера останавливает задачу до построения тяжелой CP-SAT-модели и
возвращает диагностическое сообщение. Время решения ограничивается отдельно для
каждой компоненты.

## Метрики результата

`GET /api/v1/scheduler/tasks` возвращает агрегаты:

- число событий и компонент;
- размер крупнейшей компоненты;
- количество переменных и ограничений;
- суммарное CPU-время solver-компонент;
- время и размер room matching;
- количество неразмещенных событий и предупреждений по аудиториям.

Статус `partial` означает, что сохранен пригодный частичный результат, но одна
или несколько компонент завершились ошибкой.
