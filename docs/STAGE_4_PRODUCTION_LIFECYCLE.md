# Этап 4. Production lifecycle расписаний

## Версии и публикация

Каждый `GenerationTask` является отдельной версией расписания. Для одной недели
или календарного диапазона версии получают последовательный `version_number` и
проходят состояния:

- `draft` — результат генерации и ручного редактирования;
- `published` — действующая версия, доступная для общего экспорта;
- `archived` — предыдущая или снятая с публикации версия.

Публикация новой версии автоматически архивирует ранее опубликованную версию
того же периода. Опубликованное расписание доступно только для чтения. Ручные
правки увеличивают `edit_revision`, поэтому экспорт однозначно соответствует
открытой редакции.

## Управление задачами

API lifecycle:

- `POST /api/v1/scheduler/tasks/{id}/cancel`;
- `POST /api/v1/scheduler/tasks/{id}/retry`;
- `POST /api/v1/scheduler/tasks/{id}/publish`;
- `POST /api/v1/scheduler/tasks/{id}/archive`;
- `GET /api/v1/scheduler/tasks/{id}/diagnostics`.

При запуске создаются уникальные блокировки для каждой группы в рамках недели
или диапазона. Второй конфликтующий запуск получает HTTP 409. Блокировки
освобождаются при успехе, частичном результате, ошибке и отмене.

Один расчет ограничен 14 календарными днями. Это обязательная защита памяти:
расписание университета меняется по неделям, поэтому семестр рассчитывается
последовательностью недельных задач, а не одной CP-SAT-моделью на несколько
месяцев. Дополнительно подготовка оценивает количество decision variables и
останавливает модель до передачи worker при превышении безопасного порога.

При `WorkerLostError` задача не возвращается в очередь бесконечно. Errback
переводит версию в `failed`, сохраняет диагностическую проблему и освобождает
групповые блокировки для контролируемого retry.

Для отмены сохраняются ID корневой задачи, callback и всех component-задач
Celery chord. Все они отзываются, а поздний callback не может перезаписать статус
`canceled` или сохранить частичный результат.

## Безопасное ручное редактирование

Перед сохранением сервер проверяет:

- пересечение группы;
- пересечение преподавателя;
- двойное использование аудитории;
- структурированную недоступность университета, группы, преподавателя и аудитории;
- существование активной аудитории;
- попадание даты в период версии.

При конфликте API возвращает HTTP 409 и список причин. Frontend откатывает
оптимистичное перемещение. Занятие можно зафиксировать; зафиксированные записи
нельзя удалить до разблокировки, а инкрементальная генерация сохраняет их слот.

## Диагностика

`GenerationIssue` сохраняет причины неразмещенных занятий, нехватки аудиторий и
ошибок solver-компонент. Endpoint диагностики возвращает агрегаты по типам и
детали с потоком, группой, датой и парой.

## Эксплуатационная проверка

```bash
ruff check src/app
python -m pytest
cd spa && npm run build
cd ../src && alembic upgrade head && alembic check
docker compose --env-file .env.example config --quiet
```

Перед production-миграцией обязательна резервная копия PostgreSQL. После
обновления следует проверить сценарии: параллельный запуск, отмена во время
расчета, retry, конфликтное перемещение, блокировка пары и публикация версии.
